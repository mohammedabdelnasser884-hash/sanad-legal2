## 1) المشكلة الأصلية

نظام الصلاحيات التفصيلية (`can_edit_*`/`can_delete_*`) كان مُفعّلاً بشكل صحيح فى **قسم القضايا فقط**. باقي الأقسام (الموكلين، التذكيرات، الجلسات المستقلة) لم يكن بها أي تمييز بين الأدوار — لا فى الواجهة، ولا فى الأهم: **قاعدة البيانات (RLS)**.

**الأثر العملي (قبل التنفيذ):** أي مستخدم بدور `lawyer` أو حتى `viewer` كان يقدر يعدّل أو يحذف **أي** موكل / تذكير / جلسة مستقلة فى المكتب، سواء من الواجهة أو عبر استدعاء الـAPI مباشرة — لأن سياسة RLS كانت بتتحقق من `tenant_id` بس، من غير أي فحص لصلاحية الدور.

اكتُشف أثناء المراجعة كمان إن جدول `case_sessions` جدول واحد بيخدم جلسات القضايا **والجلسات المستقلة مع بعض** (يتفرقوا بعمود `case_id`)، فأي فيكس كان لازم يفرّق بينهم بدل ما يعامل الاتنين كمفتاح صلاحية واحد.

## 2) القرار: 6 مفاتيح صلاحية جديدة

بنفس فلسفة `can_edit_cases`/`can_delete_cases` (قابلة للتخصيص لكل مستخدم عبر `profiles.permissions`، مع افتراضي لكل دور):

| المفتاح | admin | lawyer | viewer |
|---|---|---|---|
| `can_edit_clients` | true | true | false |
| `can_delete_clients` | true | **false** | false |
| `can_edit_reminders` | true | true | false |
| `can_delete_reminders` | true | **true** | false |
| `can_edit_sessions` (المستقلة فقط) | true | true | false |
| `can_delete_sessions` (المستقلة فقط) | true | **false** | false |

**منطق الاختيار:** التذكيرات أداة شخصية للمتابعة اليومية، فمنطقي إن `lawyer` يقدر يحذفها بحرية. أما الموكلين والجلسات فبيانات جوهرية للمكتب، فالحذف بالذات (مش التعديل) بيتقفل على `lawyer` زي القضايا بالظبط.

**جلسات القضايا** (`case_id` معبّى) ظلت تابعة لـ`can_edit_cases`/`can_delete_cases` الموجودين أصلاً — المفتاحان الجديدان `can_edit_sessions`/`can_delete_sessions` بيتحكموا فى **الجلسات المستقلة فقط** (`case_id IS NULL`).

## 14) ميزة جديدة: تفعيل تخصيص الصلاحيات التفصيلية وقت إضافة مستخدم جديد

**السياق:** أثناء مراجعة شاشة إدارة المستخدمين، اتضح إن تخصيص الصلاحيات التفصيلية (`can_edit_clients`, `can_delete_reminders`... إلخ) كان متاح بس فى شاشة "تعديل مستخدم" (`EditUserModal.tsx`) — شاشة "إضافة مستخدم جديد" (`UserFormModal.tsx`) كانت بتختار الدور بس (مدير/محامي/مشاهد) وتبعت صلاحيات فاضية `{}` دايمًا، يعنى المستخدم الجديد كان بياخد افتراضي دوره 100% بلا تخصيص، ولازم رجعة لشاشة "تعديل" منفصلة بعد الإنشاء عشان تظبط أي صلاحية.

**فحص الباك إند (edge function `admin-actions` — action `create_lawyer`):** أظهر إن الحقل `permissions` **كان مدعوم ومحفوظ فعليًا أصلاً** (`permissions: body.permissions || null` وقت إنشاء صف `profiles`) — الفجوة كانت فى الواجهة بس، الباك إند محتاجش أي تعديل.

**القرار:** إضافة نفس UI الصلاحيات التفصيلية الموجود فى `EditUserModal.tsx` لشاشة `UserFormModal.tsx`، عشان الأدمن يقدر يفتح/يقفل أي صلاحية للمستخدم الجديد من نفس لحظة الإضافة، لأي دور (محامي أو مشاهد).

**التنفيذ:**

| الملف | التعديل |
|---|---|
| `src/features/admin/users/EditUserModal.tsx` | تصدير `EDITABLE_PERMISSION_KEYS` (كانت داخلية) عشان تتستخدم فى الملف الجديد من غير تكرار منطق استبعاد `can_view_fees`/`can_edit_fees` |
| `src/features/admin/users/UserFormModal.tsx` | إضافة نفس بلوك الصلاحيات التفصيلية (toggle لكل مفتاح فى `EDITABLE_PERMISSION_KEYS`، بيفرّق بين "افتراضي الدور" و"استثناء صريح") — بيظهر بس لو الدور المختار مش "مدير"؛ واختيار الدور بقى يصفّر أي صلاحيات مخصصة كانت متفعّلة قبل كده (نفس سلوك شاشة التعديل) |

`can_view_fees`/`can_edit_fees` فضلوا مقفولين تمامًا فى الشاشتين، بلا استثناء. كل التعديلات إضافة صافية — صفر تغيير على منطق إنشاء الحساب نفسه (auth + profile insert).

**ملاحظة مفتوحة (برة نطاق الطلب الأصلي):** الـ`data-testid` لكل صلاحية فى شاشة الإضافة الجديدة اتسمّى `admin-adduser-permission-{key}` (مختلف عن `admin-edituser-permission-{key}` فى شاشة التعديل) عشان يتفادى أي تلخبط لو فيه تست e2e موجود بيفترض اسم معيّن. لسه محتاج تأكيدك لو عايز اسم مختلف.

**الملفات المسلَّمة:**
- `src/features/admin/users/EditUserModal.tsx`
- `src/features/admin/users/UserFormModal.tsx`

**الخطوة المتبقية:** استبدال الملفين فى نفس المسارين، وتجربة فتح "إضافة مستخدم جديد" والتأكد من ظهور وتفعيل الصلاحيات صح لكل دور.
